# DEV_DOC - 開発者向けアーキテクチャ仕様書

このドキュメントは、cub3Dエンジンの内部仕様を理解し、機能拡張や保守を行おうとする開発者に向けた技術資料です。

## 1. 現状のシステム概要 (Current System Overview)

本プロジェクトは、C言語およびMinilibX（X11）を用いて構築された、レイキャスティング（DDAアルゴリズム）ベースの3D迷路ゲームエンジンです。
Linux環境に特化して最適化されており、将来的な機能拡張（マルチプレイや動的エンティティの追加）を前提とした、疎結合かつ拡張性の高いモジュール設計が採用されています。

## 2. ディレクトリ・モジュール構造の詳細 (Detailed Directory Structure)

ソースコード（処理）とヘッダー（定義・インターフェース）が完全に分離され、さらに各モジュールが「単一責任の原則」に従ってファイル単位で細分化されています。

## 3. 現在のアーキテクチャの良い点 (Strengths)

### ① 単一責任原則に基づいたデータ構造

`t_window`, `t_config`, `t_camera`, `t_render` といった機能単位で構造体が細分化されています。各モジュール（描画関数や演算関数）には必要最小限の構造体のみが渡されるため、関数の影響範囲が明確であり、意図しないデータの書き換えが起きない安全な設計となっています。

### ② 設定値とロジックの完全な分離（マジックナンバー排除）

移動速度、UIのサイズ、各種カラーコード、解像度の限界値といった「設定値」が、ソースコード（`.c`）内に直接記述されていません。すべて `includes/` 配下の機能別ヘッダーファイルでマクロとして一元管理されているため、コードを読まずともゲームバランスやデザインの調整が可能です。

### ③ 環境最適化と完全なメモリ管理

Linux (X11) 環境に完全に特化しており、OS固有のウィンドウ・ディスプレイ破棄処理（`mlx_destroy_display`等）が適正なライフサイクルで実行されます。Valgrindを用いたテストにおいて、正常系・異常系ともにメモリリークおよび未初期化バグゼロ（`All heap blocks were freed`）が保証されています。

### ④ テクスチャの動的スケーリング

壁やスプライトのレンダリングにおいて、特定の画像サイズ（例: 64x64）に依存する計算式が存在しません。ロードした画像データから動的に縦横サイズを取得してDDAのテクスチャ座標を計算するため、任意の解像度のテクスチャを無改造で利用できます。

## 4. コーディング規約 (Coding Standards)

本プロジェクトに参加する開発者は、以下の規約を厳格に遵守する必要があります。

* **Norminette V3 準拠:** 42ネットワークの厳格なコーディング規約に準拠（1関数25行以内、変数の上部宣言など）。
* **命名規則:**
* 関数名とファイル名は `動詞_名詞`（例: `parse_map.c`, `draw_wall()`）で統一。
* 構造体は `t_機能名`（例: `t_camera`）。
* 定数（マクロ）は大文字とアンダースコア（例: `TEX_NORTH`, `FLAG_SAVE`）。



## 5. 今後の課題と拡張ロードマップ (Future Roadmap)
これはあくまで希望。無視しても良い。

Haskellによる高並行ゲームサーバーの構築
ゲームの状態（全プレイヤーの座標、鬼ごっこの鬼の判定、アイテムの取得状況）を一元管理する専用サーバーを **Haskell** で構築します。
* **採用理由:** Haskellの強力な静的型システムと純粋関数型の性質により、不正な状態遷移（チートやバグ）をコンパイルレベルで排除できます。
* **技術要素:** STM（ソフトウェアトランザクショナルメモリ）を活用し、複数プレイヤーからの同時アクセス（移動やタッチ判定）によるデータ競合をロックなしで安全かつ高速に処理します。
